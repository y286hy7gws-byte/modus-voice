# MODUS VOICE

Внутренняя платформа обратной связи для ГК «Модус Трейд»: каждый сотрудник
может подать идею, сообщить о проблеме или предложить улучшение процессов,
а руководители — рассмотреть эти обращения, назначить ответственных и довести их до
результата.

**Голос каждого сотрудника** — полный жизненный цикл обращения:
регистрация → назначение → рассмотрение → решение → результат.

---

## Возможности

- **Три роли с жёстким разделением доступа**
  - `Сотрудник (EMPLOYEE)` — личный дашборд, создание обращений (в том числе
    анонимно), только свои обращения, центр уведомлений, обсуждения;
  - `Ответственный (MANAGER)` — панель очереди решений, взятие в работу,
    статусы, запрос дополнительной информации, работа с назначенными ему
    обращениями своего и своего отдела;
  - `Администратор (ADMIN)` — полный реестр, распределение по ответственным,
    контрольные сроки, очередь «Требуют назначения», нагрузка сотрудников,
    аналитика всей компании, управление категориями и пользователями.
- **Маршрутизация по категориям**: администратор задаёт правило
  «категория → ответственный» (`Панель администратора → Маршрутизация по
  категориям`), и каждое новое обращение автоматически направляется
  ответственному. Обращения без правила попадают в очередь
  «Требуют назначения» — обращения не теряются.
- **7 статусов** с контрольной точкой принятия решения:
  `Новое → На рассмотрении → Требуется информация / Одобрено → В работе →
  Реализовано / Отклонено`.
- **6 типов обращений**, включая «Положительный отзыв» — платформа собирает
  не только проблемы, но и то, что стоит сохранить и развивать.
- **Уникальные номера обращений** (`MV-0001`, `MV-0002`, …), статусная
  история с авторами и комментариями, обязательная формулировка решения или
  причины отклонения.
- **Анонимность на уровне отображения**: автор скрыт от всех, кроме
  администратора (последний видит пометку «анонимная отправка»); автору
  собственные обращения видны с полным контекстом.
- **Комментарии и запрос информации** внутри карточки обращения
  (`Запросить информацию` переводит обращение в статус «Требуется
  информация»).
- **Центр уведомлений** (регистрация, статусы, назначения, решения,
  комментарии, напоминания о сроках) со счётчиком непрочитанных и переходом
  к обращению. Напоминания о сроках создаются автоматически при входе:
  просроченные и со сроком в ближайшие 3 дня, одно на обращение
  (дедупликация по `requestId + kind`).
- **Реестр с фильтрами** по подразделению автора, сроку
  (`Просроченные / Срок до 7 дней / Без срока`), статусу, категории,
  приоритету и полнотекстовым поиском.
- **Аналитика из реальных данных** (не набор цифр): динамика обращений,
  статусы (дуга), категории, типы обращений, реализованные идеи по месяцам,
  средний срок решения, скорость решений и доля реализованных.
- **Метрики по ТЗ (п. 2.7)**: среднее время до первого ответа, доля
  рассмотренных обращений, доля обращений с зафиксированным результатом,
  количество реализованных улучшений.
- **Повторяющиеся проблемы**: блок «повторяющихся тем» собирает категории,
  в которых за последние 30 дней открыто ≥ 2 обращения — сигнал о системной
  проблеме.
- **Вложения** (фото, документы до 3 файлов по 700 КБ) в бесплатном
  формате — base64-вложение, работает без внешнего файлового хостинга.
- **Demo Mode по умолчанию**: всё работает в браузере (localStorage),
  с готовым демо-состоянием из демонстрационного набора обращений.

## Технологический стек

| Слой | Технология |
| --- | --- |
| Фреймворк | Next.js 15 (App Router) + React 18 |
| Язык | TypeScript |
| Стили | Tailwind CSS v4 (дизайн-система в `app/globals.css`) |
| Графики | Recharts |
| Валидация | Zod (формы и API-предохранители) |
| Иконки | lucide-react |
| Хранение (по умолчанию) | Demo Mode — localStorage браузера |
| Хранение (опционально) | Supabase (PostgreSQL + Auth + RLS) |

## Архитектура

Слой данных спрятан за единым интерфейсом `Backend` (`lib/backend.ts`):

```
lib/store.tsx (AppProvider — состояние и все действия)
        │
        ▼
lib/backend.ts (интерфейс Backend)
        │                      │
        ▼                      ▼
lib/backends/demo.ts    lib/backends/supabase.ts
(Demo Mode:             (серверный режим:
localStorage,           PostgreSQL + Auth + RLS)
 seeding, RLS-фильтр
 ролей на клиенте)
```

- Демо-режим включается, **если не заданы** переменные окружения Supabase —
  ничего настраивать не нужно.
- Все вычисления KPI (реализация, средний срок решения, нагрузка
  ответственных, распределение по категориям) всегда считаются из реального
  реестра обращений, а не из заготовок.

## Интеграция с Supabase (опционально)

Если нужно серверное хранение с реальной аутентификацией и RLS:

1. Создайте бесплатный проект на [supabase.com](https://supabase.com).
2. SQL Editor → вставьте и выполните весь `supabase/migrations.sql`.
   Скрипт создаёт таблицы, RLS-политики, RPC
   (`public_stats_v1`, `create_user_v1`, `delete_user_v1`) и системные
   категории.
3. Authentication → Add user — создайте демо-пользователей
   (e-mail и пароль, `demo12345`, e-mail подтверждён), затем вставьте их
   строки в таблицу `profiles` с теми же id (готовый шаблон — в конце
   миграции).
4. Создайте файл `.env.local` в корне проекта:

```
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon/public key>
```

Приложение само переключится на серверный режим; если переменные не заданы,
продолжит работать в Demo Mode. Разграничение доступа выполняют
RLS-политики из миграции — тот же контракт, что и в демоверсии.

```

    my-requests/          — «Мои обращения» сотрудника
    manager/              — панель ответственного

    analytics/            — аналитика из реальных данных
    users/                — управление пользователями (admin)
    notifications/        — центр уведомлений
    settings/             — профиль, пароль, сброс демо-данных
  page.tsx                — вход (быстрый вход демо-ролями)
lib/
  types.ts constants.ts utils.ts rights.ts
  selectors.ts            — обогащение данных + маскировка анонимности
  analytics-metrics.ts    — метрики ТЗ (первый ответ, доли) и повторяющиеся проблемы
  seed.ts                 — демо-состояние (20 обращений, 18 категорий)
  store.tsx               — AppProvider: состояние и все действия
```

## Интеграция с Битрикс24 и 1С (концепция)

По ТЗ интеграции не требуются для хакатона, но архитектура к ним готова.

- **Битрикс24 — назначение и уведомления.** При регистрации обращения
  создаётся задача в Битрикс24 с исполнителем = ответственным по правилу
  маршрутизации; изменения статуса возвращаются вебхуком в платформу.
  Направление обмена: двустороннее (обращение → задача; статус задачи →
  статус обращения). Состав данных: заголовок, описание, автор (или
  «анонимно»), категория, ответственный, срок. Предполагаемый способ —
  REST-вебхуки Битрикс24 (`task.add`, `task.update`); уточнить перед
  реализацией: маппинг сотрудников, права сервисного пользователя и лимиты
  вебхуков.
- **1С УТ — справочники и номенклатура.** Категории «Каталог и данные» и
  «Договорная работа» требуют сверки с мастер-данными: платформа запрашивает
  карточку позиции/контрагента только на чтение, чтобы проверять актуальные
  обозначения. Направление обмена: одностороннее чтение. Способ — REST/OData
  интерфейс 1С или выгрузка-снимок по расписанию; уточнить: доступ к
  HTTP-сервисам, перечень реквизитов карточки, политика безопасности.

## Проверено в ручных сценариях

- Вход под каждой ролью, неверный пароль, быстрый вход, выход из меню,
  восстановление сессии после перезагрузки.
- Полный цикл обращения для каждой роли: создание (в т.ч. анонимно и с
  вложением) → назначение → рассмотрение → запрос информации → ответ автора →
  одобрение/отклонение/реализация с формулировкой решения.
- Видимость: сотрудник не видит чужие обращения и не получает права
  на страницы менеджера; аноним полностью скрыт от руководителя, но виден
  администратору с пометкой; ответственный получает назначенные
  ему обращения в очередь.
- Уведомления доставляются на каждое событие, читаются по одному и все сразу.
- Панель администратора: распределение, контрольные сроки, маршрутизация
  по категориям, категории (создание, переименование, скрытие из формы),
  пользователи (создание, смена роли, удаление с подтверждением).
- Автомаршрутизация: создание обращения в категории с правилом мгновенно
  назначает ответственного; без правила — обращение появляется в очереди
  «Требуют назначения».
- Фильтры реестра: подразделение, срок («Просроченные» находит `MV-0003`
  и `MV-0009`), статус, категория, приоритет, поиск.
- Напоминания о сроках: при входе ответственного или администратора
  по просроченным и близким срокам создаётся одно уведомление на обращение.
- Настройки: сохранение профиля, смена пароля с повторным входом,
  сброс демо-данных.

## Заметки к демонстрации

- Порт по умолчанию — 3000 (`npm run dev`); если занят, Next предложит
  следующий свободный — открывайте страницу, которую он укажет.
- Настройки находятся только у ролей с аккаунтом; смена пароля действует
  на текущий браузерный профиль в Demo Mode.
- Интент аналитики: все цифры пересчитываются при каждом изменении —
  смените статус на реестре и откройте аналитику снова, чтобы увидеть сдвиги.
